# Golf event notification delivery

Routine lesson events use the standard notification framework: bookings (member, guardian or professional initiated), cancellation of a booking or whole session, lesson reminders, and newly saved feedback/drills. Open groups and fixed rosters use the same booking events. Availability edits that affect no bookings do not send alerts.

Each recipient chooses Inbox, Phone push and Email per event in Notification settings. Push and email have account-wide switches as well. Unchecking every channel means no alert; email-only and combined delivery are supported independently of inbox visibility. Email defaults off and migration never opts users into it. Existing lesson booking category choices are inherited by the new lesson categories once; explicit opt-outs remain off. New announcements can select email too, subject to each recipient's preference.

Club members, administrators and coaching staff are ordinary eligible roles in the standard configuration. Golf events no longer bypass administrator role/type controls. Legacy default chair-only configuration is upgraded to the golf default role set; a version-5 administrator configuration retains its explicit role selection. Global disable, category disable, role eligibility, quiet hours, active accounts, current source and expiry are checked before delivery.

Booking confirmations go to the registered player and active club-scoped guardians with accounts. Member bookings/cancellations also notify the appointed professional unless the professional performed the action. Feedback goes only to the player and guardians; its text stays inside the booking rather than being copied into alerts. All participant alerts link directly to that booking. Guardians receive alerts according to their own preferences. A junior does not require their own login or email.

The lesson reminder queue publishes a `lesson_reminder` event at the booking's chosen lead time (24 hours by default), regardless of email-provider configuration. Delivery then uses the shared inbox/push/email paths. The old unconditional reminder banner and direct lesson email sender have been removed. In `lesson_reminder`, `sent_at` means the event was published, not that an email was sent. Reminder revision, booking ID, feedback content hash, recipient and event keys prevent duplicates and invalidate obsolete queued messages.

The durable email outbox is created in the same transaction as its notification. It retries provider failures, uses provider idempotency keys, rechecks preferences/account/access and the source before sending, honours quiet hours without using retry attempts, and stops delivering expired events. Browser database roles cannot read or modify it (RLS and grants). Reading an inbox item does not suppress an opted-in email. Push keeps its existing unread/device/permission checks.

Apply `supabase/notification_email.sql` after the golf/lesson migrations. The local demo applies it automatically and disables actual email/push delivery. Production uses the existing Resend sender configuration plus the existing VAPID configuration for phone push. `/api/cron/notifications` publishes due lesson reminders and drains both delivery outboxes; `/api/cron/lessons` also processes lessons and both outboxes. Both routes still require `CRON_SECRET`. Mutations schedule delivery after their transaction commits.

Run `pnpm test`, `pnpm typecheck`, and `node scripts/verify-notification-channels.mjs`. The HTTP check restores preferences/configuration and removes its temporary bookings, notifications and subscription. No external email or push delivery is performed in the local demo.
